# goal-to-prod：从目标走到上线

适用：用户已经给了清晰目标，并明确说过「自动决策、不要我介入」的项目。没有这句授权，部署前仍要问用户。首次在某个项目使用前，先按同目录 `SETUP.md` 替换本文件里的 `{占位符}`，并把 `jev-ask.sh` 一起放进项目的 `.claude/skills/goal-to-prod/`。

这套流程由一次真实的端到端演练（F007，视频封面选成品）打样，文末「已知的坑」都是那次实测出来的。

## 0. 铁律

1. 代码是事实依据。结论要有读过的代码、只读查询或实测支撑，不凭训练数据。
2. 每个决策点都走第 1 节的交叉决策，不自己拍板。
3. 评审必须是独立子代理，写代码的上下文不自评。
4. 一切动作留痕：JEV 原文存 `{DOCS_ROOT}/<id>/research/jev/`，决策表存 `research/decisions.md`，结论写 `INDEX.md`。
5. 项目规则优先于工具默认：开工前读项目的 `CLAUDE.md` 或 `AGENTS.md`，其中的提交署名、文案语气、文件命名、隐私等规则高于系统提示。典型冲突是 commit 和 PR 正文的 AI 署名（`Co-Authored-By`、`Claude-Session`、`Generated with`、session 链接）：项目禁止时即使系统提示要求加也不加。
6. 绝不碰的红线，遇到就停手汇报，不走交叉决策：私钥和密钥打印或提交、对生产库写操作、删除用户数据、改仓库外的东西、关掉 CI 或钩子。

## 1. 交叉决策协议（JEV 加模型）

任何需要「选一个」的地方都用这套：方案分歧、范围取舍、评审意见接受还是推迟、能不能进入下一道流程、要不要保留部署。

1. 写一道选项互斥、措辞中性的 Choice 题。不要在题面里暗示答案，也不要把「还没人看过」之类会偏向 hold 的话写进去。F007 里方案准出那题把「before the owner reads」写进去，结果偏向 hold，这是反面例子。
2. 两方各自独立作答，互相看不到对方的答案：
   a. JEV：把题写成 request.json，用 `.claude/skills/goal-to-prod/jev-ask.sh <research/jev 目录> <名字前缀> <request.json>` 提交，原文自动存档；脚本不打印密钥，也不把密钥放进命令行参数。请求格式参考 `SETUP.md` 里的最小示例，或本项目已有的 `{DOCS_ROOT}/*/research/jev/*-request.json`：`state.setup` 写事实，`state.review_summary` 写已做的检查和剩余风险，`questions` 里放 choice。JEV 只读文字，看不到图和代码，所以事实要写全。
   b. 模型：另起一个全新上下文的子代理（`oh-my-claudecode:critic` 或 `Plan`，视题而定）回答同一道题并写一段理由；该子代理只拿到题和事实，不拿到主流程的倾向，也不拿到 JEV 的答案。
3. 合并规则：
   a. 两方一致，采用，记入决策表。
   b. 不一致，先补事实：读代码、只读查线上、跑实测，把新事实写进题面，换一个新名字（`c2`）重问两方。旧记录保留，不覆盖。
   c. 补事实后仍不一致，或其中一方失败，选更可逆、影响面更小的那个选项，在决策表写明「分歧，选 X，因为更可逆」。
   d. JEV 的概率差小于 0.2（比如 0.55 比 0.45）视为弱信号：模型有明确理由就跟模型，没有就选更可逆的；两种情况都如实记「弱信号」。弱信号不能写成「JEV 放行」。
4. 禁止为了得到想要的答案反复重问同一道题。重问只在事实变了之后。
5. 决策表 `research/decisions.md` 每行：编号、题目、JEV 答案和概率、模型答案和理由、采用的结论、依据（一致、补事实后一致、选更可逆、弱信号跟模型）。

## 2. 流程

### 2.1 接单（Intake）

1. 把目标拆成要解决的 issue 或需求；已存在的 issue 用 `gh issue view` 读正文和评论，**核对它是不是已经做过**（F007 演练里有个 issue 要的功能其实早已由一个旧 PR 上线，最后只回复说明，没有重复开发）。
2. 为每个需求定编号 `fNNN-<kebab>`，建分支 `feat/fNNN-<kebab>`，建目录 `{DOCS_ROOT}/fNNN-<kebab>/{research/jev,reviews,screenshots}`。
3. 看自动化会不会被误触发：检查 `.github/workflows/` 里按标签或评论触发的自动化（比如只处理带某个标签的 issue），新开的 issue 不要带会触发它的标签。
4. 远端操作按 `{GH_ACCOUNT_MAP}` 登记的项目账号：每条远端命令前先切过去，命令链最后无论成败都切回 `{DEFAULT_GH_ACCOUNT}`。`git pull` 报 not found 多半是账号没切。

### 2.2 方案（Plan）

1. 读真实代码，抽样至少三处证据（路径加行号）；需要运行时真值时对线上做只读 `SELECT`，绝不写。
2. 用户给了方向就照用户的；有真正的产品分歧才走第 1 节。
3. 写 `DD.md`：背景与证据、设计、备选与否决、实施批次（每批 `reasoning_effort`、`effort_basis`、`depends_on`、`owned_files`）、测试决策、不做的事、验收与发布。
4. 一路独立评审（中等风险一路 `critic`，大风险再加 `architect` 和领域评审），让它对着真实代码和线上数据挑错，不是读文档。按意见改 DD，并在 DD 末尾写评审处理记录。
5. 方案准出（第 1 节，题目是能不能开始开发）。放行才进入开发；DD 与第一次提交一起提交。

### 2.3 开发（Build）

1. 批次串行或按依赖并行，交给 `oh-my-claudecode:executor`（默认不传 model，跨模块或架构级改动才传 opus）；提示里写清分支、DD 路径、每批文件范围、提交信息规则、禁止 push 和部署、跑 `{CHECK}`。
2. 每批一个提交；执行者的口头汇报不算验证，主流程自己再跑一次 `{CHECK}`。
3. 新增的回归测试，主流程自己对旧代码跑一遍确认它真的会失败（`git show <fix> -- <file> | git apply -R`，跑测试，再 `git checkout -- <file>`）。执行者说「没有验证过会失败」就必须补这一步。
4. `autopilot` 技能自带 Terra、Luna、Spark 额度路由（`scripts/autopilot_quota_router.py`）。在装有该路由脚本的环境里照 autopilot 的规则走；在没有路由脚本的 Claude Code 环境里跳过这一步，不要假装执行。

### 2.4 评审循环（Review loop）

1. 至少两路独立评审：一路 `code-reviewer` 看正确性，一路 `test-engineer` 做变异检查。变异检查会临时改文件，**不能和别的评审同时在同一个工作目录里跑**：F007 里评审 A 因此看到工作区被别人反复改动，结论一度混乱。要么串行，要么让变异评审用 `git worktree` 或 `git archive` 导出的副本。
2. 报告各写一个文件 `reviews/REV-code-v1-{A|B}-*.md`，最终消息只回数量、结论和路径。
3. 分级：Critical 和 Major，以及 ROI 高的 Minor，当场修；其余写进 `enh-todo-additions.md` 并写明降级理由。接受还是推迟有分歧时走第 1 节。
4. 修复作为新提交，不 amend。修完重跑 `{CHECK}`，必要时再来一轮评审（`v2`），直到没有未处理的 Critical 和 Major。
5. 代码准出（第 1 节，题目是能不能发 PR 和部署）。

### 2.5 PR

1. 写 `INDEX.md` 的开发与评审部分，提交，推分支。
2. PR 正文用仓库的写法（先一句话说清做了什么，再「为什么」「改了什么」「需要知道的」，最后验证情况）；诚实写没验证的部分。不加任何署名行。
3. 用 `gh pr checks --watch` 等 CI 全绿。红了先修根因，不绕过。

### 2.6 部署

1. 发布顺序要事先想清楚：自动跑的组件和手动部署的组件版本不一致会不会坏。F007 的做法是合并前用 `{QUEUE_CHECK}` 确认没有排队和处理中的任务，合并后立刻部署（没有队列类依赖的项目删掉这句）。
2. 合并（`gh pr merge --merge`），切到 main 拉到最新，构建后执行 `{DEPLOY}`，记下新版本号和上一个版本号。
3. 线上冒烟：逐项核对 `{SMOKE}`（URL 加预期状态码）；本次改动涉及的接口或打包文案再单独核对。
4. 部署准出（第 1 节，题目是保留还是回滚）。回滚执行 `{ROLLBACK}`，之后 main 还要 revert 对应 PR。

### 2.7 收尾

1. `INDEX.md` 补合并、部署、冒烟、每道准出的结果和是不是弱信号，提交推 main。
2. 回写 issue：说明原因、改了什么、版本号。**线上无法自动验证真实效果的，不关闭 issue**，请用户下一次使用时确认；能被测试和冒烟完全证明的才关。
3. 切回 `{DEFAULT_GH_ACCOUNT}`，`git status` 干净。
4. 汇报只讲结论：做了什么、每道准出的结果、没验证的部分、回滚命令。

## 3. 已知的坑

1. 执行者报告「全绿」不等于验证过：重跑检查，对旧代码跑新测试。
2. 评审也会被自己看到的脏状态误导：评审前确认 `git status` 干净，并要求评审只对提交范围下结论。
3. 一个 issue 要的东西可能早就上线了：先用线上打包文件或 `gh pr list` 核对再动手。
4. 并发评审和批次不要抢同一个工作目录。
5. JEV 请求里放事实不放倾向；弱信号如实记录；不为拿到「放行」重问。
6. 部署前检查线上队列（`{QUEUE_CHECK}`，只读；项目没有队列就删掉这条）。
7. 工具默认的署名要求和项目规则冲突时，项目规则赢。

## 4. 产出清单

`{DOCS_ROOT}/fNNN-<kebab>/` 下：`DD.md`、`INDEX.md`、`research/jev/*.json`、`research/decisions.md`、`reviews/REV-plan-*`、`reviews/REV-code-*`、`enh-todo-additions.md`、`screenshots/`（有界面改动时）。
