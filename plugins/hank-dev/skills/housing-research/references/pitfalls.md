# 踩坑清单（2026-10 South Yarra 实战）

## 需求理解（返工最多）

- **规则层级**：把「客厅卧室都是地毯禁止」当硬淘汰，结果 22 套被错误排除。用户的意思是全屋满铺地毯不喜欢、降权，可移除的小块地毯没关系。开工前把每条规则写成硬、软、权重三层并复述。
- **「带家具」的定义**：用户指床、桌子这类实际家具，不是洗碗机。只看文字会把 23 套写了 Furnished 的房源误判成没家具，要靠照片逐项确认，并在排名表加「家具」列。
- **现住的楼不是候选**：Haiku 的两套排到第一，用户一句话指出那就是自己住的楼。需求里的「现住地址」要用来排除同楼房源。
- **「面积（如有）」**：多数房源页和户型图没有总面积，列里写「未标」，不要估。

## 数据

- 搜索关键词 `furnished` 会命中 `unfurnished`；详情页再判。
- 上游调研和实时页面会不一致（价格、是否带家具、账单），交付前以实时页为准。
- 挂牌几小时到一天就可能下架：页面跳回首页就是已下架。没取到图库的房源要先检查是不是下架了，而不是直接放占位。
- Google 评分：页面没渲染、只落到楼里商铺、评论只有几条都会发生，不要把「没取到」写成「没有」，不要把别栋楼的评分配给这栋。
- 竣工年份几乎都来自聚合站，冲突就并列写出并标低置信度。
- 步行时间是估算，同街的两栋可能被定位到同一点。

## 浏览器

见 skill `revium-browser-test` 的 `references/real-browser-takeover.md`。要点：不用 Playwright 起浏览器去碰有反爬的站；接管用户自己的 Chrome；每次新连接都要用户点 Allow 或用 `mac-approve`；标签读完就关，结束核对数量；不起第二个 Chrome 实例（曾导致用户的 Chrome 崩溃）；图库读页面内嵌数据，不点界面。

## Jev

- 决策问题没把硬条件和扣分项分开，Jev 把软条件当淘汰理由。
- 决策档位写得太宽，几乎全是「值得看」，没区分度；写成可检验的条件。
- 只给文字，Jev 看不到照片里的床和桌子：要把代理看图的结论放进状态。
- 局部重问，不要全量重跑。
- 权重和扣分数值是助手的设定，告诉用户。

## 并行与多代理

- 同一个 Chrome 同一时间只能有一个进程驱动；并行的代理只做网页检索和看图。
- 代理的结论会互相矛盾或不确定（带 confidence），保留它们，不要抹平。
- 后台任务很慢（浏览器标签在后台加载慢）：给等待加上限，先对入围的前 30 名核对，不要全量。

## PPT

- 手工抄 `/_blob` id 容易错：每套只传 3 张拼图。
- 表格列宽不够会让一行折成两行，整页溢出：先算好百分比，缩短文字。
- 重新打分后名次会变，摘要里的名次要从数据取。
- 用户反对空白页：任何位置都要有图或说明，不留灰块。
- 用户在 artifact 上的评论要回复并解决。

## 收尾

- 清掉自己创建的临时资源（专用 Chrome profile 目录等）。
- 数据、脚本、照片、报告归档到案件目录并更新索引，不留散落副本。
