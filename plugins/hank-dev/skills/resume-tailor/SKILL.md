# hank-dev:resume-tailor：简历定制与双代理审查

核心原则：**内容以真实经历为准。** 所有陈述必须能追溯到真实项目经历、真实数据、或用户提供的一手证据（LinkedIn 截图、绩效记录、项目文档）。不允许为了迎合 JD 关键词而编造头衔、项目、数据。遇到"这个技能我到底有没有"的分歧，以用户口头确认为准，不要自己脑补。

---

## 工作区约定

首次触发时，检查当前项目下是否已有简历工作区（默认 `resume/`，如果用户已有别的目录约定，以已有目录为准，不要重复创建）：

```
resume/
├── master/
│   ├── cv-zh.md              # 中文 master CV，纯净版（不含决策注释，可直接导出）
│   ├── cv-en.md               # 英文 master CV，纯净版
│   └── cv-annotated.md        # 带注释版：每段为什么这么写、依据哪份证据，供你自己审阅
├── jd/
│   ├── INDEX.md                # 跨 JD 索引：日期 | 公司 | 岗位 | 状态 | 本轮关键改动
│   └── {日期}-{公司}-{岗位slug}/
│       ├── JD.md                # 原始 JD 全文或截图转录
│       ├── tailored-cv-{lang}.md
│       └── cover-letter-{lang}.md
└── evidence/                    # 可选：LinkedIn 截图、绩效记录等一手证据存放处
```

若目录不存在，先问用户放在哪（很可能是求职专用文件夹而非当前代码仓库），再建骨架，不要假设路径。

## 主流程

### Phase 0：上下文确认
若 `resume/master/cv-annotated.md` 已存在，读它了解已有的写作决策和踩过的坑，避免重复犯同样的错误（例如"叙述过度 AI 化"这类曾经被打回的问题）。

**若 master CV 还不存在（第一次触发本技能）**：不要直接跳去 Phase 2 按 JD 定制，先引导用户从零建一份 master CV。问清楚：核心工作经历（公司/岗位/时间/职责/量化成果）、教育背景、技能清单，以及能佐证这些经历的一手证据（LinkedIn 截图、绩效记录、项目文档）。基于这些真实输入产出第一版 `cv-zh.md` / `cv-en.md` / `cv-annotated.md`，再进入 Phase 1 打磨。

### Phase 1：Master CV 打磨
只打磨通用主线内容，不针对具体岗位关键词。每次修改前，确认改动依据（真实经历 / 用户新提供的证据 / 表达优化），修改后同步更新 `cv-annotated.md` 里对应段落的注释。

### Phase 2：按 JD 定制
1. 读 JD 原文，提取硬性要求关键词（技术栈、年限、职责动词）与软性偏好（行业、团队规模、工作模式）。
2. 基于 master CV 生成 `tailored-cv-{lang}.md` 和 `cover-letter-{lang}.md`：只做**表达层面**的裁剪、排序、侧重调整（哪些经历放前面、哪些细节展开），不新增 master CV 里没有的内容。
3. 生成带备注版和不带备注版两份（备注版供你审阅决策依据，不带备注版才是真正要投递的文件），避免两种用途混在一份文件里影响审阅。

### Phase 3：双代理独立审查（并行，两个视角互不知情）
用 Agent 工具并行拉两个独立评审，两者看到的都是同一份定制稿，但互不共享对方的评语（避免互相锚定）：

- **ATS agent**：只看关键词覆盖率、格式可解析性（表格/图标/多栏排版会不会让 ATS 解析器读乱）、量化陈述是否充分（有没有把职责动词换成"做了什么 + 影响多大"）。产出：命中/缺失关键词清单 + 格式风险点。
- **HR agent**：站在目标市场（默认澳洲/墨尔本本地招聘市场，用户可指定其他市场）招聘者角度，评估叙述是否自然、是否有"一读就是 AI 生成"的痕迹（套话堆砌、过度总结性形容词、破折号式转折）、经历是否讲清楚"这个人到底解决了什么问题"。产出：竞争力评分 + 具体改写建议。

两个 agent 的 prompt 里必须明确写清各自的评审边界，不要让 ATS agent 评论表达自然度，也不要让 HR agent 挑关键词覆盖率，边界混了会导致两份报告互相重复、抓不住重点。

### Phase 4：应用改动 + Diff 复核
应用 Phase 3 的修改建议后，用同样的两个 agent 对新版本再跑一轮，对比：
- ATS 关键词命中率前后变化
- HR 竞争力评分前后变化
- 是否还有未采纳的高优先级建议（若有，说明为什么不采纳）

这一轮的前后对比是判断是否达到「何时算完成」（见文末）的辅助信号，不是独立的停止标准；两轮提升幅度很小，通常就意味着两个 agent 已经收敛到只剩低优先级建议，两处标准应该是同一个结论的两种表述，不要分开判断。

### Phase 5：归档
- 更新 `resume/jd/INDEX.md` 加一行：日期、公司、岗位、投递状态、本轮关键改动一句话。
- 如果本轮发现了某个通用的、可复用到其他 JD 的表达优化（不是针对这个岗位专属的），同步回 `master/cv-annotated.md`，避免同样的问题在下一个 JD 定制时重新踩一遍。

---

## 何时算完成

满足以下任一即可停止本轮打磨，交给用户自己决定是否投递：
- ATS agent 和 HR agent 都只剩低优先级/风格偏好类建议，没有硬性缺失
- 用户明确喊停（"先到这里"/"够了"/"提交一下方案先"）

不要把"再打磨一轮说不定更好"当作继续迭代的理由，打磨简历是收益递减的事，明确的停止信号出现就停。
